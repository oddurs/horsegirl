# Instructions for agents

You are working in horsegirl, an agent-first diagram language written in Rust.
Follow these rules exactly. They are enforced by hooks and by CI.

## The workflow

1. Run `scripts/agent take` to take the next ready item, or
   `scripts/agent take <id>` for one item. It names the branch, makes the
   worktree, claims the item and prints it as your prompt.
2. Work only in the worktree it names. Never work in the primary checkout, and
   never share a worktree.
3. Make the change. A bug fix arrives with the test that would have caught it.
4. Run `scripts/agent check` until it passes.
5. Commit with `scripts/agent commit '<type>(<scope>): <subject>'`.
6. Tick each acceptance criterion that is now true with `cairn tick <id> <n>`.
   Tick what you watched pass, not what would let you close.
7. Run `scripts/agent finish`. It refuses while a criterion is unticked. Then
   it closes the item, commits the backlog and opens the pull request, set to
   merge when CI passes. Use `--no-auto` when a review comes first, and
   `--body-file <file>` to state what a reviewer should doubt.
8. Run `scripts/agent land` to bring the branch up to date, push it and wait
   until it merges. Then run `scripts/agent done <branch>`.

If you cannot finish, run `cairn release <id> --reason '<why>'` and say what
you learned in `cairn note <id> '<text>'`.

## Hard rules

- Never commit or push to `main`. It advances only through a merged pull request.
- Never use `--no-verify`, `|| true`, or a skipped test to make a check pass.
- Never name an assistant, a model or a tool vendor in a commit, a pull
  request, a comment, a document or a file path.
- Never change `priority`, `milestone` or `due` on an item. Propose the change
  with `cairn propose <id> <field>=<value> --why '<reason>'`.
- Never add a dependency without stating in the pull request what it replaces.

## The task seam

All automation uses these commands and no others:

```
scripts/task fmt        format in place
scripts/task fmt:check  verify formatting
scripts/task lint       clippy with warnings denied, shellcheck, the backlog check,
                        the site lint and type check
scripts/task test       the full test suite
scripts/task test:core  the core tests, natively and in WebAssembly
scripts/task build      compile, and export the site into site/out
scripts/task check      all of the above
```

## Commits

Conventional Commits. Imperative subject, at most 72 characters, no trailing
period. The body says why. End with `Refs: <id>` for the backlog item.

## Where things are

- `docs/design.md`: what horsegirl is and the decisions already made.
- `docs/conventions.md`: code and writing conventions.
- `cairn.toml` and `cairn/items`: the backlog and its schema.
- `site/`: the website, a Next.js static export. Read the guides in
  `site/node_modules/next/dist/docs/` before you change it: they match the
  installed version.
- `ROADMAP.md`: generated by `cairn render`. Never edit it by hand.

## Roadmap and issues

This project tracks its roadmap and issues with `cairn`. Every item is a Markdown file under `cairn/items`, described by the schema in `cairn.toml`.

**Do not create ad-hoc TODO, PLAN or NOTES files.** Create a cairn item instead, so the work appears on the board and in the generated roadmap.

### The loop

1. `cairn next --view agent` — what is ready to start. It excludes anything blocked by unfinished dependencies and puts work already in progress first.
2. `cairn claim <ID>` — take it before you start, so no one duplicates the work. `cairn claim --next --view agent` picks and claims the top-ranked unclaimed item in one step. Then read `cairn prompt <ID>`: the item with everything it rests on — the outcome it serves, what its dependencies concluded, what done means and what earlier runs learned.
3. Do the work. Record what you learn: `cairn set <ID> <field>=<value>` for fields, `cairn note <ID> "<TEXT>"` for anything that needs a sentence — why you chose something, what you tried, what to watch for.
4. `cairn tick <ID> <N>` as each acceptance criterion becomes true — `cairn show <ID> --criteria` lists them numbered. Tick what is true, not what would let you close.
5. `cairn close <ID>` when it is done, or `cairn release <ID>` to hand it back.
6. `cairn check` before you report finished. It must pass.

### Commands

```sh
cairn next --view agent --json                 # ready work, ranked
cairn claim --next --view agent                # take the next ready item
cairn search <TEXT> --json        # titles, bodies and labels
cairn list --json                 # all open items
cairn list --filter 'blocked=false,priority=p0'
cairn prompt <ID>                 # the item as a prompt, with what it rests on
cairn show <ID> --json            # one item, including its body
cairn new "<TITLE>" --type <TYPE> --milestone <MILESTONE>
cairn set <ID> status=<STATUS>    # also labels+=x, or any field below
cairn note <ID> "<TEXT>"          # append reasoning; never replaces
cairn show <ID> --criteria        # acceptance criteria, numbered
cairn tick <ID> <N>               # tick one; --all for every one
cairn close <ID>
cairn check                       # validate; run before finishing
cairn render                      # regenerate ROADMAP.md
```

Selection uses saved view `agent`. Additional filters only narrow it; the view's sort and columns do not change `next` ranking. Over MCP, pass `{"view":"agent"}` to `next_items` and to `claim_item` without an id. A direct claim is an explicit assignment outside this selection policy. Regenerate these instructions with `cairn agent --view agent --write AGENTS.md`.

Claims coordinate writers in the same item directory and are seen across the worktrees of this repository: `next` leaves out what another worktree has claimed, `claim` refuses it, and `cairn worktrees` shows what each is doing. Separate clones are not read. Agree on assignments before splitting work across clones.

Items are numbered: `0012`, and commands accept the bare number too. Write the number in `depends_on` and other id references. Each item also carries a `uid` tag; leave it alone. If a merge gives two items one number, `cairn renumber` moves the one that arrived and retargets the references that came with it.

### Schema

- **Types**: `feature`, `bug`, `chore`, `docs`, `spike`, `decision`, `lens`, `milestone`, `track`
- **Statuses**: `backlog` (open), `planned` (open), `doing` (active), `blocked` (open), `done` (done), `dropped` (dropped)
- **`priority`**: one of p0, p1, p2, p3 — Within its milestone. p0: the release does not ship without it; p1: planned for it; p2: wanted; p3: optional — **you may propose this in a note, not set it**
- **`effort`**: one of s, m, l, xl — A rough size, never a date. xl means: split it or write a spike.
- **`area`**: one of language, model, check, lens, layout, render, describe, cli, mcp, interop, bench, wasm, site, workflow, release — The subsystem that changes
- **`risk`**: one of low, medium, high — How wrong this can go. high: review it line by line, and an agent does not start it unasked. — **you may propose this in a note, not set it**
- **`surface`**: one of none, language, diagnostics, cli, mcp, svg, theme — The public contract this changes. Anything but none needs a changelog entry, and language needs a benchmark run.
- **`due`**: date, YYYY-MM-DD — A committed date, YYYY-MM-DD. Set on milestones only. — **you may read this and not set it**
- **`pr`**: free text — The pull request that carries the work
- **`related`**: names any items, by id, several allowed — Items worth reading with this one. Not an ordering; use depends_on for that.
- **Milestones**: `v0.1` (due 2027-01-31), `later`, `v0.2` (due 2027-03-31), `v0.3` (due 2027-06-15), `v1.0` (due 2027-09-30)
- **Saved views** (`cairn list --view NAME`): `now`, `next`, `agent`, `human`, `triage`, `waiting`, `dependencies`, `spikes`, `decisions`, `contracts`, `lenses`, `site`, `later`, `history`

### Rules

1. Before starting work, find or create the item and set it to an active status.
2. Use the fields above rather than inventing new ones; add new fields to `cairn.toml` first.
3. Never hand-edit the generated roadmap file — change items and run `cairn render`.
4. `cairn check` must pass before the work is considered done.
