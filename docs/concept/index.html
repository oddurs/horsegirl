A concept. No horsegirl code exists yet.

Agents write what is true.
You choose how to look.

horsegirl is an open source diagram language for the case where an agent writes the diagram and a person reads it. State the facts once. A lens turns them into a flow, a sequence, a matrix, or a picture with no name yet.

This window is a toy of about 350 lines. It reads the five rules and redraws on every key press. Its layouts are simple, and the flow lens starts from positions set by hand. The real engine does not exist yet.


  

    
For the agentFive rules to learn. Every error names its fix. A read-back stands in for eyes.

    
For the readerPictures that stay put between edits. Plain by default, with alt text written for you.

    
For the repositoryOne file of facts and many pictures. Rules that fail the build. A diff a reviewer can read.

  






  

    
The language

    
Five rules. That is all of it.

    
A person learns the language from this table. An agent learns it from the same table. There is one syntax for every kind of picture, and nothing in it needs an id, a quote or a bracket.

  

  

    
A name is a thing.Names can have spaces. A thing exists as soon as you mention it. You never declare an id and then give it a label.

    
Web app


    
An arrow is a link.Commas fan out. Words after the colon label the link. A crossed arrow is a link that must not exist. A question mark is a guess.

    
Web app, Mobile app -> API gateway: HTTPS
Web app -x Postgres: never directly
Orders -> Cache ?


    
Braces hold what is inside and what is known.A bare name inside braces is a part. A key: value pair is a fact. Facts can go on links too.

    
Services { Orders, Payments, Notify }
Payments { owner: Commerce, calls: 4000 }


    
A story is links in the order they happen.Outside a story, a link is always true. Inside a story, the order you write is the order of events.

    
story checkout {
  Orders -> Payments: charge
  Payments -> Notify: paid
}


    
A lens says what position means.The same facts feed every lens. A file can ask for many pictures.

    
show flow
show sequence of checkout
show rings from Payments

  






  

    
The idea underneath

    
Every diagram type is the same graph with different dials.

    
Charts solved this problem years ago. A bar chart and a scatter plot are the same data with fields bound to different channels. Diagrams never got that grammar, so each type became its own small language.

    
horsegirl gives diagrams the grammar. A lens binds a field such as step, owner or depth to a channel such as x, y, inside, radius or thickness. A sequence diagram is a graph where down means later. A swimlane is a graph where each row is an owner.

A new diagram type is a few lines

      
The built-in lenses are written in the same language a user writes. Nobody waits for a maintainer to add a diagram type. Somebody writes a lens, and a new kind of picture exists.

    

    
lens rings {
  focus:  one thing
  radius: hops from focus
  colour: owner
}

lens lanes {
  x: step
  y: owner
}

  






  

    
New pictures

    
Eight pictures from facts you already wrote.

    
Each one is a single show line. Two of them need numbers, and horsegirl reads those from a file. That is where diagrams and data visualisation become one subject. Six of the eight have no equivalent in Mermaid. Volume and Weight exist there as Sankey and treemap, each with its own syntax and its own copy of the data.

  

  

    

    

    

    

    

    

    

    
  






  

    
Agent first

    
An agent cannot see. So the tool sees for it.

    
An agent that writes Mermaid works blind. It cannot tell whether the file parses, whether the picture overlaps, or whether the picture says what it meant. horsegirl answers all three in text, so the agent finishes the loop before a person looks.

  

  

  

    
Principle 1The whole language fits in a prompt.No model has seen horsegirl. So the specification is one page, and the tool prints it. An agent reads the page once and can write the language.

    
$ horsegirl spec
1 A name is a thing. Spaces are fine.    Web app
2 An arrow links things. Commas fan out. A, B -> C: label
3 Braces hold parts and facts.           G { A, B }  A { owner: X }
4 A story is links in order.             story S { ... }
5 show picks a lens.                     show flow | sequence of S
                                         lanes of S | matrix | rings from T
-x forbids a link.  A final ? marks a guess.
One fact per line. Order is free outside a story.
End a line with  @ path:line  to cite evidence.
Run check after every edit. Apply the fix it returns.


    
Principle 2Forgiving reader, strict writer.Models carry habits from Mermaid. The reader accepts them and says what it changed. The formatter writes one canonical form, so every file in a repository looks the same.

    
- "Web app" --> "API gateway" : HTTPS;
+ Web app -> API gateway: HTTPS

note[N0101]: read `-->` as `->`, dropped quotes and `;`


    
Principle 3Every error carries its fix.A message names the place, the cause and the exact replacement. It also ships as JSON, so the agent applies the fix without reading prose. The parser reports every error in one pass.

    
error[E0412]: `Paymnts` looks like a typo
   --> checkout.horse:15:13
15 |   Orders -> Paymnts: charge
   |             ^^^^^^^ used once, one letter from `Payments`

{"code":"E0412","line":15,"fix":{"from":"Paymnts","to":"Payments"}}


    
Principle 4Eyes without a vision model.describe reads the picture back as text: what it shows, how big it is, and whether anything overlaps. The agent compares the read-back with what it meant to say.

    
$ horsegirl describe checkout.horse --lens "lanes of checkout"
7 steps across 5 owners. 6 handoffs.
Starts at Web app (Apps). Ends at Email provider (External).
Drawn at 796 × 266. 0 overlaps. 0 crossings. All labels fit.


    
Principle 5Facts cite their evidence.An agent that reads code can attach the file and line to each fact. verify finds facts whose evidence has moved or gone. A diagram can no longer rot in silence.

    
Orders -> Payments: charge  @ src/orders/pay.ts:41
Orders -> Postgres: save    @ src/orders/repo.ts:17

$ horsegirl verify checkout.horse
stale: src/orders/repo.ts:17 no longer mentions Postgres


    
Principle 6An edit is an added line.One fact sits on one line. Order does not matter outside a story. Saying a fact twice does no harm. So an agent appends, and never rewrites a file it only half remembers.

    
$ horsegirl add checkout.horse "Orders -> Cache -> Postgres"
+ Orders -> Cache
+ Cache -> Postgres
  2 facts added. 1 new thing. 0 things moved in 3 pictures.


    
Principle 7The file is the agent's map.A horsegirl file is twenty lines that describe a whole system. An agent reads it faster than it reads the code, and can ask it questions. The person gets the picture. The agent gets the graph.

    
$ horsegirl query checkout.horse "what reaches Postgres"
Web app -> API gateway -> Orders -> Postgres

$ horsegirl query checkout.horse "owners on checkout"
Apps -> Platform -> Commerce -> Growth -> Platform -> External


    
Principle 8A picture has a budget.Agents write too much. A diagram with sixty boxes helps nobody. Past the budget, the compiler folds groups into single boxes and says what it folded.

    
note[N0300]: 61 things is over the budget of 25
   = folded 4 groups: Services (14), Data (9), Edge (7), Jobs (11)
   = draw one with:  show flow of Services


    
Principle 9The syntax is decided by measurement.A public benchmark asks several models to write diagrams with only the one-page spec. A syntax change that lowers the score does not ship. Taste loses to data.

    
$ horsegirl bench --models 3 --tasks 200
valid on first try      target 99%
valid after one fix     target 100%
read-back matches task  target 95%

Themes

    
Plain by default. Yours in one file.

    
The pink belongs to the project, not to your diagrams. The default theme has no brand. It takes its font from the page it sits in and follows light and dark mode, so a horsegirl picture in your docs looks like your docs.

    
Pick a theme. Every diagram on this page changes, including the live editor at the top.

Level 1Pick a theme.One word, on the command line or in the project settings. The facts file stays free of style, so the same file draws for a slide, a README and a terminal.

    
# horsegirl.toml
theme = "blueprint"
dark  = "auto"        # follow the reader's system


    
Level 2Change a few tokens.A theme is twelve tokens. Start from a built-in one and replace what differs. A brand usually needs an accent, a font and a palette.

    
theme ours {
  from:    plain
  accent:  #0B6E4F
  font:    Inter
  corner:  2
  palette: #0B6E4F, #D97706, #7C3AED
}


    
Level 3Let the page decide.The SVG reads CSS variables and gives each shape a class named for what it means. A docs site restyles every diagram from its own stylesheet, with no rebuild.

    
.docs svg.horsegirl {
  --hg-accent: var(--brand);
  --hg-font:   inherit;
}
.docs .hg-thing.owner-commerce { --hg-fill: var(--brand-soft); }


    
Level 4Bring your design tokens.A team with a design system already has these values. One command turns a token file into a theme.

    
$ horsegirl theme from tokens.json --name ours
  wrote themes/ours.horse  (12 tokens, light and dark)


    
The limitColour follows meaning. Nobody paints one box.Mermaid lets a file set the fill of a single node. Agents write horsegirl files, and an agent should not choose colours. A dial binds colour to a fact, and a rule sets emphasis.

    
show flow { colour: owner }
show flow where tier is critical { emphasis: strong }

# not in the language, on purpose
# Payments { fill: #ff00aa }


    
The guardA theme must pass a check.A custom theme can make a diagram unreadable. The tool measures contrast and tests the palette for colour-blind readers before it accepts a theme.

    
$ horsegirl theme check ours
ink on paper       14.8 : 1   pass
accent on paper     5.9 : 1   pass
palette 2 vs 3      too close for red-green colour blindness
   = fix: try #B45309 for palette 2

  

  
The token count, the variable names and the check output are proposals. The four themes here are a sketch of the built-in set.






  

    
For the people

    
Two things that keep the human readers.

  


  

    

      
Stability

      
Layout that survives an edit

      
Most engines solve the whole picture again after each change. One new node can move every other node. Readers lose their place and diffs in review become noise.

      
horsegirl treats the previous layout as an input. The engine keeps each existing node where the reader last saw it and finds room for the new one.

      

        
        
      

    

    
  


  

    

      
Compatibility

      
Your Mermaid files already work

      
A new language with no importer starts with no users. horsegirl reads Mermaid directly and draws it with its own layout engine. A team can switch renderers first and switch languages later, or never.

      
convert rewrites a Mermaid file as horsegirl source. Once the facts are in horsegirl, every lens works on them.

      
The road also runs the other way. draw --to mermaid writes a Mermaid block, so a README renders on GitHub today, before any host supports horsegirl.

    

    
  






  

    
The opening

    
Every current tool wins on one axis and loses on the other.

    
Mermaid is everywhere because GitHub renders it and it needs no install. Its layout is the common complaint. The tools with better layout never got the reach. Nobody holds the top right corner.

  

  

    
    

      
Mermaid
Renders on GitHub with zero setup. Layouts overlap and cross. Large diagrams become unreadable.

      
D2
Clean language. Its best layout engine is a separate paid product, and a label change can rearrange the whole picture.

      
PlantUML
Widest set of diagram types. Needs Java. Looks like 2009.

      
Graphviz
Strong graph layout. A terse language and dated output.

Where the syntax comes from

    
Borrowed from five projects. Fixed in three places.

    
None of the parts is new. The combination is, and so is the length: the whole language is five rules.

  

  

    
From D2 and Graphviz
The arrow, the braces, and things that exist when you mention them. These are the parts of existing languages that people learn without reading documentation.

    
From Structurizr
One model, many views. Structurizr proved that teams want it. It is limited to the C4 architecture views.

    
From Vega-Lite
Bind a field to a channel and let the compiler work out the scales and the layout. This is the grammar of graphics, applied to graphs.

    
From Penrose
Keep what a diagram says apart from how it is drawn. Penrose pays for this with three files and a lot of setup. horsegirl keeps one file.

    
From storyline research
A layout where lines meet when things interact. The research is twenty years deep and no text language exposes it.

    
Fixed: Mermaid's traps
In Mermaid, a node named end breaks the file, a bracket in a label changes the node's shape, and each diagram type has its own rules. horsegirl has one grammar and its keywords appear only at the start of a line.

  

  

    
Where this language design is weak

    
    
      
  • No model has seen this language. Every model has seen Mermaid. The one-page spec, the forgiving reader and the benchmark exist to close this gap. If the benchmark shows they do not, the syntax must move closer to what models already write.
    • 
      
  • Names with spaces need a careful grammar. A name cannot contain ->, a colon, a comma or a brace without quotes. This rule needs testing on a few thousand real diagrams before it is safe.
    • 
      
  • Things that exist on mention hide typos. Paymnts becomes a new node. The answer is a check: a name that appears once and is one letter from another name is an error.
    • 
      
  • A lens needs its fields. show lanes is useless if nothing has an owner. The compiler must say which facts are missing, and never draw a wrong picture.
    • 
      
  • A lens is short to write and hard to lay out. Each family of lens needs its own solver. The plan is four solvers (layered, grid, nested, radial) and every lens picks one.
    • 
    

  






  

    
Architecture

    
One core. Every surface is a thin shell.

    
The core is a single Rust library that compiles to a native binary and to WebAssembly. The command line, the browser, the editor and the agent all run the same code and get the same bytes out.

  

  

  

  

    
No browser, anywhere
Mermaid needs a headless browser to measure text on a server. horsegirl ships font metrics inside the binary. The same input gives the same SVG on every machine.

    
No server either
The playground is a static page that runs the WebAssembly build. The project needs a package registry, release binaries and a docs site. It has no backend to operate.

    
The parser never gives up
A half-typed file still produces a tree and a partial diagram. Editors need this for live preview. Agents need it to get every error in one pass.

  






  

    
The hard part

    
Layout is four steps, and the fourth is where diagrams get ugly.

    
This is the layered solver, the one the flow lens uses. The method is public knowledge. Graphviz and ELK both use it. The open work is orthogonal routing around groups and the stability rule.

Adoption

    
How it takes over, one step at a time.

    
horsegirl cannot ask GitHub for native rendering on day one. It starts where nobody has to be persuaded. An agent picks the tool that gives it the fewest errors. People meet horsegirl as a picture in a pull request, and no step asks them to give anything up.

  

  





  

    
Open source, on purpose

    
Rules that keep the project worth trusting.

  

  

    
The best layout is free
No paid engine and no watermark. The feature that makes horsegirl better is in the open repository.

    
The spec is the product
The language has a written specification and a public test suite. Anyone can build a second implementation, and the project wants one to exist.

    
Permissive licence
MIT or Apache-2.0, so editors, docs platforms and hosts can embed the core without a legal review.

    
No breaking the picture
After 1.0, a file that drew last year draws the same this year. Layout changes ship behind a version line in the file.

    
Lenses belong to everyone
A lens is a text file in the same language. People share lenses the way they share themes. The core stays small enough for one person to read.

    
Honest gallery
Every example in the docs is drawn by CI from source in the repository. No picture is touched up by hand.

What Rust costs

      
    
        
  • Fewer contributors. More people write TypeScript. The answer is that lenses and themes are written in horsegirl, so most contributions never touch Rust.
    • 
        
  • A bigger download in the browser. A WebAssembly core is larger than a small JavaScript layout library. The build needs a size budget that CI enforces.
    • 
        
  • Slower experiments. Layout work is trial and error, and Rust compiles slowly. The scene format lets a layout idea be tested from any language first.
    •
